# Linux on the Zynq PS

Linux runs on Zynq's ARM Processing System (PS) and controls RSD in the Programmable Logic (PL). This is not Linux running on RSD itself. See [System architecture](en-fpga-zynq-arch) and the [build, SD-write and execution instructions](en-fpga-zynq-synth-for-linux).

## Boot components

Vivado/Vitis 2019.2 generates the RSD bitstream and FSBL. Buildroot 2025.02.19 builds the ARM toolchain, U-Boot, Linux and rootfs. Outputs are under `Processor/Project/Vivado/ARM_Linux/Build/images/`.

- `boot.bin`: packages FSBL, bitstream and U-Boot.
- `uImage`, `rsd-zed.dtb`, `extlinux.conf`: kernel, device tree and boot configuration.
- `rootfs.ext4`: rootfs with OpenSSH and `rsd-loader`.
- `rsd-zedboard.img`: partitioned image for writing to the whole SD card.
- `rsd-zedboard_ed25519` and `.pub`: client SSH keys generated by default. The private key is not included in the image.

Networking defaults to DHCP. Use `RSD_ROOTFS_OVERLAY` for initial settings such as static IP and DNS. SSH uses root public-key authentication; password authentication is disabled. See the build instructions for details.

## Loading a program

Transfer `code.hex` via SSH/SCP and run on the board:

```bash
rsd-loader /root/code.hex
```

The loader is installed during the build. It validates the HEX size before loading it into RSD memory; no manual size argument is needed. It displays program UART output. Press Ctrl-C to exit the loader.

## Memory and control

ARM and RSD share external DDR. ZedBoard's 512 MiB is split into fixed regions:

| Physical addresses (inclusive) | Use |
| --- | --- |
| `0x00000000–0x0FFFFFFF` | PS Linux |
| `0x10000000–0x1FFFFFFF` | RSD |

The loader finds `rsd-ram`, `rsd-pl2ps` and `rsd-ps2pl` through `/sys/class/uio/uio*/name` and maps the corresponding `/dev/uio*` nodes. It does not depend on UIO numbering. The [DRAM controller](en-fpga-zynq-mem-controller) translates RSD internal addresses to ARM physical addresses; these are distinct from the [RSD memory map](en-arch-mem-map).

After RTL changes, regenerate the bitstream, boot.bin and SD image, then reboot. The old kernel's `/dev/xdevcfg` write procedure is not used in this flow. Image generation and PS Linux in QEMU have been validated; board boot and RSD execution on hardware have not.
